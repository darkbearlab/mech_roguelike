# 機體 Roguelike — v0.1 架構規格

給 Claude Code 的交接文件。這份只界定**第一版架構**:座標、移動模型、行動經濟、回合結構與介面骨架。數值一律標示為暫定,可調參數全部進 JSON。細節與後續內容由設計者另行討論。

---

## 0. 專案定位

- 純 **roguelike**,不是 roguelite。單機體、永久死亡、單局內成長,無局外進程。<--可討論 可能為了現代化玩家會取捨
- 題材:日系人形機體,**開闊地形**作戰。開闊地是題目而非缺陷——張力來自「從遠距火網下切進去」的那段暴露。
- 平台:**手機瀏覽器優先**。直式,單手拇指可操作。
- 兩條互相耦合的軸:**向量移動**(慣性、承諾)與**行動點/熱量經濟**(取捨、透支)。

### v0.1 的完成定義

一台玩家機體與數台敵機,在一張開闊六角地圖上,能用向量移動與單一武器互相擊毀。移動慣性、朝向與速度分離、行動點透支、熱量,四項機制實際可玩且可調參。

**v0.1 明確不做**:武器種類、部位損傷、掉落與回收、戰役層、座艙皮膚、敵人裝備抽取、技能。只留掛勾。

## 1. 技術架構

沿用設計者既有專案已驗證的分層,不要偏離:

```
core/      純邏輯,無 DOM、無 canvas、無隨機來源以外的副作用
render/    canvas 繪製
ui/        觸控盤、儀表、選單
data/      所有平衡數值的 JSON
tests/     core/ 全覆蓋
bot/       無介面的自動對局,用來產生基線數據
```

- TypeScript,無框架,canvas 2D。
- **core/ 不得 import render/ 或 ui/**。所有平衡數值來自 `data/*.json`,不得寫死在邏輯裡。
- 亂數必須走可注入的 seeded RNG,讓 bot 對局可重現。
- 從第一天就要有 `bot/`:能跑 N 場並輸出勝率、平均回合數、平均命中率、平均熱量峰值。之後每次改平衡都靠它比對。

## 2. 座標與網格

- **六角格,flat-top(平頂),axial 座標 `(q, r)`**。
- 六個方向依序編號 0..5,對應 `N, NE, SE, S, SW, NW`:
  - `0 N  = ( 0, -1)`
  - `1 NE = (+1, -1)`
  - `2 SE = (+1,  0)`
  - `3 S  = ( 0, +1)`
  - `4 SW = (-1, +1)`
  - `5 NW = (-1,  0)`
- 距離用標準 cube 距離:`(|dq| + |dq+dr| + |dr|) / 2`。
- **移動、射程、感測、視線全部使用這同一把尺**,不得有第二套度量。

選 flat-top 的理由:六個方向剛好排成 `[NW][N][NE] / [SW][S][SE]` 的 3×2 觸控盤,與設計者既有的左盤指位一致。

### 次格精度

位置與速度在 core/ 內部一律以 **1/10 格為單位的整數**儲存(常數 `SUB = 10`),避免浮點誤差。

- `posSub: {q: number, r: number}` — 單位 1/10 格
- `velSub: {q: number, r: number}` — 單位 1/10 格每回合
- 佔格、視線、射程等遊戲判定一律使用 `round(posSub / SUB)` 得到的整數格。
- 顯示速度時換算成「格/回合」保留一位小數。

## 3. 移動模型(向量)

### 3.1 每回合的移動解算

單位輪到自己時,依序:

1. **加速宣告**:玩家選一個方向(0..5)、或「巡航」(不加速)、或「制動」。
2. **套用加速**:`velSub += dir * accel`(制動則將 `velSub` 朝反向縮減 `accel`,不得越過零)。
3. **套用阻力**:`velSub` 的長度減少 `drag`,不得越過零。
4. **速度上限**:長度夾在 `maxSpeed` 以內。
5. **位移**:`posSub += velSub`。
6. 沿舊格到新格的六角直線,**逐格判定**經過事件(碰撞、地形、經過敵人射界)。動畫也走這條線。

單位在位移期間**不重新徵詢輸入**。承諾就在這裡:你只在第 1 步做決定,其餘全是物理。

### 3.2 驅動型態決定加速量值

`accel = round(thrust / mass * SUB)`,結果與 `drag`、`maxSpeed`、轉向規則一併由驅動型態決定。暫定三型:

| 驅動 | accel | drag | maxSpeed | 轉向 | 側向加速 | 產熱 |
|---|---|---|---|---|---|---|
| 履帶 | 4 | 4 | 20 | 1 AP 轉 1 面 | 不可 | 低 |
| 步行 | 6 | 6 | 18 | 每回合免費 1 面 | 不可 | 中 |
| 噴射 | 12 | 2 | 40 | 免費任意 | **可** | 高 |

**關鍵**:`drag` 也由驅動決定,而非全域規則。

- 地面驅動 `drag ≈ accel`,意思是不加速就在一兩回合內停下——**步行機體幾乎沒有慣性,手感可控、隨時可改主意**。
- 噴射 `drag` 遠低於 `accel`,**慣性只在你選擇噴射時才買進來**。

同時具備腿與推進器的機體在兩種régime 之間切換(切換本身是一個行動,見 §4)。

「側向加速」指加速方向不在機體朝向的前方三面之內。只有噴射可以,這是側滑射擊的來源。

### 3.3 朝向與速度分離

- `facing: 0..5`,與 `velSub` 完全獨立。
- 朝向決定:**武器射界**(前方三面)、**感測品質**、以及未來的裝甲正面。
- 速度向量指東北、朝向正東 = 側滑著開火。這是本作動態感的核心,務必讓它在第一版就能發生。
- 轉向成本見上表。

## 4. 行動點與熱量

### 4.1 行動點(節拍器)

- 每回合配額 `apQuota = 1`(可調)。
- 行動成本 1..3。**允許透支**:成本超過當前可用 AP 時仍可執行,差額成為債務。
- `apDebtCap = 2`。債務會在後續回合**優先扣抵配額**,還清前不能做新的行動。
- 債務 > 0 期間:**不得散熱**,且命中率 −10%。這是可讀的脆弱視窗(見 §7 敵人喊話)。
- **緊急切斷**:立即清零債務,代價是熱量大幅上升 + 該系統進入短暫故障。這是難看但存在的脫身選項。

暫定成本表(進 `data/actions.json`):

| 行動 | AP | 熱 |
|---|---|---|
| 待機 | 0 | 0 |
| 鎖定 | 1 | +2 |
| 射擊(輕) | 1 | +6 |
| 射擊(重) | 3 | +20 |
| 裝填 | 2 | +2 |
| 換武器 | 2 | 0 |
| 散熱 | 1 | −25 |
| 切換驅動模式 | 1 | +5 |
| 轉向(履帶) | 1 | 0 |

### 4.2 熱量(真正的經濟)

- `heat`,上限 `heatCap`(暫定 100)。
- 來源:行動(上表)+ 加速(依驅動,噴射每 10 sub 的加速 +4 熱)。
- 每回合被動散熱 `heatPassive`(暫定 −3)。
- `heat > 70%`:命中率 −15%。
- `heat >= 100%`:**強制停機一回合**——不能行動、不能加速,但阻力照常作用(噴射機會繼續飄)。

行動點是節拍器,熱量才是貨幣。「散熱」的真正代價是那一回合什麼都沒做。

## 5. 回合結構

v0.1 採**循序回合**,不用時間單位排程器:

```
回合 N:
  玩家階段:  加速宣告 → 位移解算 → 行動
  敵人階段:  逐一,每台同樣是 加速宣告 → 位移解算 → 行動
  世界階段:  熱量被動散熱、狀態計時、勝敗判定
```

- 玩家永遠先手,敵人依陣列順序。
- 一個單位的加速與位移**在自己的階段內立即解算**,不延到回合末。理由是可讀性優先——玩家要能看見自己這一步跑到哪裡,再決定開不開火。

> 待決:同時移動(全員先宣告、再一起解算)在向量制下更精確,但呈現困難很多。v0.1 先做循序,把解算順序抽成一個可替換的模組。

## 6. 戰鬥判定

單一武器即可,先跑通管線。

```
命中率 = 基礎命中
        − k1 × (自身速度 / SUB)
        − k2 × (目標速度 / SUB)
        + (自身速度 == 0 ? 穩定平台加成 : 0)
        − 熱量懲罰
        − 債務懲罰
        − 距離衰減
```

暫定:`基礎命中 = 75%`,`k1 = 4`,`k2 = 3`,`穩定平台加成 = +10%`。全部進 `data/combat.json`。

**這條公式是兩條軸的耦合點,不可省略。** 沒有它,移動盤與功能盤就是兩個各玩各的小遊戲:高速沒有代價,煞停沒有回報。有了它,「衝進去還是停下來打」才是每回合都要重新判斷的問題。

- 傷害:基礎值 + 小幅浮動,再減護甲(浮動),護甲穿透削減減免比例。
- 射界:目標必須落在朝向的**前方三面**之內。
- 視線:六角直線,被地形阻擋則不可見、不可射。

## 7. 敵人(v0.1 最小可行)

- 與玩家共用同一套移動與行動規則,不得走捷徑。
- 行為只需三態:`巡邏 → 警戒 → 交戰`。狀態轉換本身消耗一個行動。
- 決策足夠簡單即可:有射界且命中率高於門檻就開火,否則朝可改善位置的方向加速。
- **喊話式意圖預告**:敵人下一個行動以浮動文字顯示在其上方,免費、不需玩家解鎖——框架是「聽見對方喊出戰術術語」,而不是預知能力。債務狀態同樣外顯。

## 8. 地圖

- 開闊地形為主。單張手工地圖即可,尺寸暫定 40×40 六角。
- 每格屬性:`terrain`、`elevation`(整數)、`dragModifier`。
- 地形型別暫定:
  - `開闊` — 無修正
  - `碎石` — `drag +2`
  - `稜線` — 阻斷視線,不可進入
  - `高地` — `elevation +1`,感測範圍加成
- 視線規則:六角直線上若有格子的 `elevation` 高於起點與終點,則阻斷。
- 開闊地的結構由**高低差與稜線**提供,取代傳統 roguelike 的牆與走廊。

## 9. 介面

直式手機。上方地圖佔滿主畫面,下方左右兩盤。

### 左盤 — 移動

- 3×2 六向按鈕:`[NW][N][NE] / [SW][S][SE]`,對應方向 5/0/1 與 4/3/2。
- 另有 `巡航`(不加速)與 `制動` 兩鍵。**巡航是正式選項,不是省略**,而且大概是最常按的一鍵。
- 每個方向鍵上顯示按下去的預測落點(小箭頭或幽靈標記)。
- 若該方向對此驅動屬側向加速且不被允許,按鍵置灰。

### 右盤 — 功能盤(即座艙)

- 依機型換配置與外觀。v0.1 只做一套,但**資料結構要允許每個機型定義自己的功能盤佈局**。
- v0.1 按鍵:鎖定 / 射擊 / 裝填 / 換武器 / 散熱 / 待機。
- 每鍵顯示 AP 成本與產熱。會造成透支的按鍵以警示色標示。

> **不要**做「每台機體把同一功能放在不同位置」。那考驗手指與記憶,不是判斷,在永久死亡下會讓玩家覺得被陰。機型差異應落在**能知道什麼**上——有的座艙只有熱量警告燈而無數值、有的只顯示遠/中/近而無精確距離、有的沒有後方攝影機。v0.1 只需把這個資訊層抽成可設定的欄位,先全開。

### 儀表

速度(格/回合,含方向指示)、朝向、熱量條、AP 與債務、彈藥。

### 相機

沿用既有專案的結論:相機跟隨預設關閉,提供 OFF / SNAP / PAN 三段;夾制範圍是可觸控的遊戲區而非視窗。拖曳可平移地圖,附回中鍵,移動後自動回中。

## 11. 待決問題(設計者會另行討論,先留介面)

1. 循序移動 vs 同時移動——解算順序需可替換。
2. 加速量值是否還要細分「起步」與「續推」(起步昂貴、續推便宜,用經濟手段強化承諾)。
3. 護甲模型:比例吸收 vs 全額吸收,以及是否每次受擊獨立擲點。
4. 座艙資訊層的具體欄位清單。
5. 局內熟練度(首次搭乘新機型的時間懲罰,隨該局遞減)。
6. 撞擊:高速撞上稜線或彼此的處理。

---

## 12. 建置順序建議

1. 六角座標與繪製、觸控盤骨架。
2. 向量移動與驅動型態(先無敵人,單機在圖上跑,確認慣性手感)。
3. 朝向與射界、視線。
4. 行動點、透支、熱量。
5. 單一武器與命中公式(耦合速度)。
6. 敵人三態與喊話預告。
7. `bot/` 自動對局與第一份基線數據。

第 2 步跑起來就該先讓設計者試手感,再往下走。
